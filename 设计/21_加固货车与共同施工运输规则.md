# 加固货车与共同施工运输规则

状态：2026年11月1日本轮已实现，地区专项42项通过；自然改装与真实页面验收由根代理单独记录。本轮只把既有地方货车从64容量付费改装为128，不含铁路、新列车或24席客运。

## 解锁与筹办

地区运输已启用、曾取得home首城资格、urbanworks已研究、当地已兑现publicWorks，且处于associated/integrated或已经取得市政议约，才可以在原生地区节点事件里选择“筹办货车改装”。事件会先列出木120、铁20、零件8、工具8、两名当地施工者和180秒工期；完工后的每趟额外零件成本是0.05。

筹办只登记工程，不立即扣走home全部材料、不加床位或人口、不增加第二辆车，也不提前修改载重。每条路线只能改装一次；已有公共项目、市政或公用工程正在备料/施工时不能筹办改装，反过来也一样。已完成项目的旧空车可以继续返程，新项目仍需等唯一货车空闲才发货。

## 实际送料与施工

改装成本合计156单位，必须由原64容量货车分批运到该地方。物资依次从home仓离开、属于在途货物、进入改装buffer；不进入地方普通可用仓。每笔接收保存真实shipmentId、材料数量和到达时间，重复回调、复制货单、错误工程ID不能再入库。

所有工程货物与正常贸易交替：旧公共工程优先，其次货车改装，再公用工程与市政；任意一趟工程之后，下一趟先履行普通贸易。优先级不创造并行车队，也不能越过已有路线占用。缺少部分材料时可以先运可支付的部分，同时留下木料、旅粮和已升级路线的零件维护费。

最后一批材料实际抵达后，buffer按156单位配方消费一次，工程进入building。**同一辆车留在地方改装**，保存为空车返程方向、status='refitting'，不再跑另一趟贸易；路线继续占用原两名home运输工，另需两名当地真实成年builder推进180秒。

当地健康不足30、施工者退休或不足两人时暂停，已消费材料、货车位置和工期保留。道路中断不阻止已经位于地方的改装，但完工后空车需等通路恢复才可返回。两名当地builder不能同时推进市政、公用工程和货车改装。

完工只把该路线capacity由64改成128，释放当地builder，并让原空车沿原路返回。其他路线仍是64；运输仍每路一车、两人、原路程与贸易合同，既有客运人数不变。

## 成本与在途边界

出发时一次支付原货物、木1与旅粮；已完成改装的路线另付0.05零件。没有零件就暂停新发车，不自动欠账。额外零件费只在未来新趟次出发时收取，旧在途货车和刚改好的空返车不追扣；返航不退旅耗或维护费。

新shipment保存出发时capacity。旧货单缺此字段按64解释，即使路线后来升级到128也不重新解释旧货单载重。新车按128限额校验真实装货，Municipal及Services接收实际route.capacity；右侧仓库不因容量提高而增加任何物资。

途中断路仍沿现有规则原地保留材料，可以带未交付材料返回原home仓。退回材料只入仓一次，改装buffer不会因此增加，未完工程仍等待后续送料。已经交付的材料不因暂停运输或返空车再退给home。

## 状态和模块边界

配置在`content/regions.js`的`CivilRouteUpgradeContent`，规则在`CivilRegions`，不覆盖`regions.projects`的旧publicWorks工程，也不覆盖Municipal或Services项目。

```js
c.regions.upgrades = {
  nextId: 2,
  projects: {
    river: {
      id: 1,
      status: 'supplying', // building / complete
      required: {wood:120, iron:20, parts:8, tools:8},
      buffer: {},
      remaining: 0,
      receipts: [], // {shipmentId, cargo, at}
      startedAt: 0,
      completedAt: null,
      refitShipmentId: null
    }
  }
};
```

`upgrades`延迟到首次筹办才建立。合法旧档缺字段继续使用64容量，不因加载新版补材料、补车辆或改写工程；显式null/false及损坏的新账拒绝导入。已有改装凭据只能读取和推进，不能再次初始化领取容量。

对外接口：

```js
CivilRegions.upgrade(s, id)
CivilRegions.upgradeActive(s, id)
CivilRegions.upgradeEligible(s, id)
CivilRegions.canUpgrade(s, id)
CivilRegions.startUpgrade(s, id)
CivilRegions.nextUpgradeCargo(s, id, capacity) // null | {projectId,cargo}
CivilRegions.receiveUpgradeCargo(s, id, cargo, upgradeId)
CivilRegions.validUpgradeShipment(s, shipment)
```

货单使用`purpose:'upgrade', upgradeId`；共享公用工程使用`purpose:'services', serviceProjectId`。它们与原`trade/project/municipal`共用Regions唯一车队与运输岗位。

Municipal把building阶段的改装和Services项目计入同一builder容量；三个模块分别在开工时检查其他模块是否已有活动工程。Services.projectAvailable表达施工占用，不能要求一个已关联的合法公共工程节点必须先额外签市政议约，才能升级自己的货车。

存档校验将路线128容量绑定到已完成改装记录，回执材料合计绑定到buffer或已消费配方，building阶段绑定到留在地方的真实refitting货车。伪造容量、缺车施工、重复回执、错方向、错误工程编号和旧货单超载都拒绝。完工时间至少晚于最后到料180秒，不能修改一个状态字符串就通过容量校验。

## 验证范围

`node --test tests/regions.test.cjs`共42项通过，其中本轮新增8项覆盖：

- 解锁条件、三类工程互斥、不瞬扣材料、不覆盖旧公共项目。
- 原64车分批送料、唯一buffer入库、回执与材料守恒。
- 断路退回未交付材料，不返还旅耗，不变造已交付库存。
- 原车留地、两名真实施工者、退休暂停、跨年与读档保持。
- 完工只升级单路线，后续每趟真实支付0.05零件。
- 旧货单缺字段兼容、错容量/错编号/缺车/坏字段拒绝。
- 与真实Municipal接线后，128份材料实际运到市政工程。
- 与真实Services接线后，128份材料实际运到公用工程，且三个工程互斥。

原publicWorks专项按新交替贸易规则等待中间一趟真实贸易后才收到第二批材料；没有缩短道路时间或跳过施工。上述是离线规则验证，不把测试fixture的材料和人口称为自然游玩成果。
