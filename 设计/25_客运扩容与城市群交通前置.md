# 客运扩容与城市群交通前置

2026年11月1日。本文规格已完成代码实现和306项完整回归；浏览器自然研究、施工、24人首趟和第十四任接续已验收，证据见文末。依据代码提交`2dcff7c`及设计16、24扩展三独立来源；原8人旅队保留，新装备提供24人能力，始终全局最多两组。铁路与城市群仍未实现。

## 1 最小选择：先扩大道路迁居组织

新增可施工的“迁居车组装备”，每套支持一支最多24人的家庭迁居队，仍全局最多两支旅队。装备表示加固行李车、老幼乘用车具、帐篷和组织器具；居民可以随队步行，**不称为24座汽车、客运列车或已经修好的铁路**。

既有Urban是来源直接到指定接纳点的抽象旅程，单程120秒、返程120秒。本切片只增加单趟可服务人数，不缩短时间，不新建地理位置模型。Regions仍是home向河谷／铁轨／高地的径向实物货运，单程分别60／90／120秒，车辆64或实付改装后的128载重。两种任务共享真实home运输工与对应道路通行条件，但不能把128货箱换算成128旅客，也不能把Urban的120秒当作已建铁路路程。

选择道路组织作为下一步，是因为现有来源、车队、钢材、施工和家属准入已经齐备；可以单独验证人口与维护守恒。设计16的轨道、站场、机车、客货班次是后续独立切片，不作为这次扩容的隐藏前提。

## 2 研究与真实资产

| 项目 | 确定规格 |
| --- | --- |
| 新科技ID／名称 | `passenger_transport`／迁居运输组织 |
| 技术前置 | `logistics`、`standards`、`steel` |
| 发现条件 | 历史首城旗`urban.city`，且至少一个Origins来源已签批次协议；不要求当前400／1000／3000人口 |
| 研究成本／时长 | home知识120、钢20、零件12、工具16；480模拟秒 |
| 工程ID／名称 | `passengerfleet`／迁居车组装备，仅home可建，最多2套 |
| 每套材料 | home木180、铁40、钢24、零件16、工具20，开工一次实付 |
| 每套施工 | 2名实际home营建工`servicebuilder`，360个实际工作秒 |
| 每套能力 | 一项同时占用的24人迁居任务资格；新增2个`transporter`岗位席，**不赠送工人** |

复用CivilServices的home工程事务、已付材料、工时和竣工记录，不加第二套工程仓或施工队。与home当前水站、学校、住宅等公用工程共用一个施工槽；没有两名实际营建工就暂停，不补工时、不退款。建成后才有装备和新增岗位席，禁止Room瞬建获得运力。

资产ID由该项真实竣工记录推导，如`service_project_6`。不得只存“已解锁大队=true”；两次不同竣工产生两项不同资产，单一资产不能同时供两支队使用。不要再把同一套装备登记为Regions货车。

两套装备加研究总费用为木360、铁80、钢68、零件44、工具56、知识120，不含原有车队场。若第二座车队场尚未建成，仍须按当前规则另付木180、铁20、零件8、工具10，不能直接把岗位上限改成16。

不要求特定四轴政体、制宪、国家或共同财政。技术和工程使用现有本地仓库；来源议约、地方同意接纳及已有公民资格继续分别核验，不能借运输升级强迫吞并来源。

## 3 人手、资产与维护

| 任务 | 原小队 | 新大队 |
| --- | ---: | ---: |
| 批次人数 | 1—8 | 9—24 |
| 实际home运输工 | 2 | 4 |
| 专用装备 | 无新要求 | 一套空闲且真实竣工的迁居装备 |
| 每人旅费 | 粮6、药0.2、工具0.2 | 相同 |
| 每次发车额外维护 | 不加新费用 | 木2、零件0.2、工具0.5 |
| 往返时间／发车间隔 | 去120＋回120／全局至少120秒 | 相同 |

24人满载一次总付粮144、药4.8、工具5.3、木2、零件0.2。固定维护按一整次装备出动收取；9人小规模使用大队也需同样固定维护和4名运输工。人数不超过8时直接按原小队处理，不占新装备、不收大队维护。

维护在**出发前一次付清**，覆盖本趟往返；在途不因home后来缺零件而被重新扣费或禁止返乡。空闲装备无周期维护，暂不另做耐久百分比、燃油或电力系统。运输工沿用home名册与日常口粮，不额外创造4名随队居民，也不再扣第二份居民口粮。

`Urban.reservedTransport`改为逐旅队累加其固定`crew`，不能继续`parties.length * 2`。去程、候床、带人返乡、空车返程全程占用人手；新装备同样占到整趟返回结束才释放。没有第三支旅队，没有按来源各赠两队。

三条既有货运线占6人，两支大队占8人，合计需要**14名实际运输工**。现有两座车队场仅12席；两套装备各加2席后可达16席，玩家仍须实际调岗。只有一座车队场时，建两套装备也仅10席，不能同时包办三货运线与两大队。

劳力不足时：已承诺旅队按全局partyId先后获得完整班组，未获足2／4人的队伍暂停移动，年龄与旅粮照常推进；已承诺人手不释放给新任务。Regions继续从同一总在岗数减去全部旅队承诺后核定货运，禁止每个模块各取完整运输岗。这里同时补足旧小队移动时的人手核验，但旧队所需仍固定2人，绝不追改为4人。零成年恢复不依赖这套调度，见第5节。

## 4 发车是一个事务，大队不挤掉家庭责任

默认模式`auto`：有空闲装备、4名可用运输工和足够费用时优先安排大队；否则尝试原小队。第一套装备真实完工后才出现原生“规模：大队优先／维持小队”切换，不另开交通面板。

一次发车按下列顺序完成：

1. 检查全局少于两队、120秒发车间隔、来源与目的地、道路、同意接纳资格。
2. 只读计算可用装备、完整班组、目的地空床和来源名册，尝试满足全部条件的最大批次；大队候选为24至9人，小队为8至1人。
3. 每一候选都用真实年龄名册检查来源总留守、三段育龄、岗位、教养、120秒粮药及额度；同时检查目标自己的住房、医护、教学和粮药。本地支付**旅费加维护全部费用后**仍保留home120秒口粮，不能用地方粮仓替付。
4. 来源报价、两端准入、装备和人手都有效后，才一起支付全部费用、提交来源扣人、写回执和加入旅队。任何提交前失败均零变更；若扣费后来源revision失效，原样退回这一笔实际扣款，不保留装备占用或空旅队。
5. 新旅队加入后，只读其出发快照。装备、研究、界面规模或来源选择后来变化，都不能修改在途人数、班组、目的地、已付费用或剩余路程。

大队缺维护、缺4人、缺装备或目标只能接纳小家庭时，可自动回退到真实可付费的小队，文字明确“本次按小队接纳”及原因。回退前不能先扣大队维护；两种方案都失败则停发新任务。关闭自动接纳只停止新发车，不召回或删除在途的人。

Origins不能只把`choose`中的8改成24：现算法直接放宽会变成21成人＋2儿童＋1老人。新大队按最多三个原8人家庭组，从同一份逐次扣减的候选名册选人；有完整年龄结构时为15成人、6儿童、3老人。部分组仍用原1—8规则，不足年龄成员不凭空补齐。合并重复cohortId，保留原身份和年龄，最后按完整迁出名册重新核验留守及供养。每个9—24候选都须正整数、逐cohort守恒。

## 5 在途、返乡和恢复不改人口规则

所有旅队仍只由Urban每600模拟秒老化一次，18成年、65退休、80离世；大队不是一次成人奖励。目的地按实际候床人数预留住房，来源按未完成安置的实际存活旅客保留返乡床位。死亡只释放死者的床位，抵达才释放来源原住处，真实返乡则把预留转为现居。

河网的`legacyHousingOverflow`依旧最多16且单调下降，**不能因24人能力改成48**。两个新来源始终为0。24人任务从第一趟就正确预留，不存在新增“历史超住”借口。

道路关闭、撤回安置许可、缺床和缺公共服务沿用当前位置与原目标：途中停等可退回已走路段，已经抵达目标的返程必须等待该道路修通。不能把维护不足当成把旅客直接传送回源的理由。已有2×24人的名册不能在切换小队时截成2×8。

旅粮仍是出发实付的每人6粮；每10秒按在途实际存活人数×0.12扣，24人初始上限144。正常240秒去回与最多120秒候床都在500秒人均旅粮预算内。超长断路仍沿用现有“消耗至0、寻求返程并保留名册”的模型，不新增免费补给，也不声称本切片已实现饥饿死亡或物理救援。后续救援必须另有真实运输合同。

已联系来源的单人到访始终只需home实付6粮、合法来源成人和本地空床，仍只去home；不需要新科技、装备、2／4名运输工、药、工具或批次议约。没有这些运力时仍能手动采粮、接纳一名真实成人，再逐步恢复岗位。来源本身的留守与可迁成人限制不取消。

## 6 精确存档与兼容合同

保留Urban现有schema1和Origins现有schema2，不因扩容重建任何人口账。新增独立运输元数据模块，建议`CivilPassenger`与`civilization.passenger`。下列数字仅为格式示例，必须读取接入当时的模拟时刻和urban.nextParty，不能写成固定默认值：

```js
{
  schema: 1,
  introducedAt: 45742,
  legacyBeforePartyId: 120, // 首次接入时原urban.nextParty；以后不变
  preference: 'auto',      // 或'small'
  lastDepartureAt: null,   // 新批次最后一次实际出发时刻
  legacyReadyAt: 45845     // 首接入elapsed + 当时旧dispatchClock，不随切换计划清零
}
```

该对象不保存人口、仓库、独立运输工或另一份装备数量。装备只从home的Services合法竣工记录推导，忙闲只从真实在途任务引用推导。

新批次旅队保存不可变的`transport`快照；非dispersed来源的迁出回执保存相同快照，并逐字段核对：

```js
{
  schema: 1, profile: 'road24', capacity: 24, crew: 4,
  assetId: 'service_project_6', departedAt: 46000, initial: 24,
  paid: {food:144, medicine:4.8, tools:5.3, wood:2, parts:0.2}
}
```

新小队使用`road8/capacity:8/crew:2/assetId:null`，实付为实际初始人数的原旅费，木和零件为0。新singleton回执的transport为null，不占车辆。`initial`是出发人数；有人离世后，费用与容量快照不能按现存人数改写，`rations`才按真实消费减少。

兼容与校验必须同时满足：

- 加载合法旧档时仅增加passenger元数据，不生成装备、岗位、研究、材料或人口；旧在途队伍及旧Origins历史回执原字段逐字保留。缺transport的旧批次按8席、2工读取，不猜过去实付金额或出发秒数。
- 旧缺字段兼容只允许编号小于固定`legacyBeforePartyId`，且符合原8人全部边界。新编号必须有快照，不能删掉快照降成旧记录。
- 原始旧档可以先通过旧形状校验再初始化；出现新科技、客运工程、24人快照等证据而整个passenger模块缺失时拒绝，不重新登记cutoff掩盖损坏。显式null／错误schema不修复。
- 两套资产都必须有实际Services竣工与付费记录；profile只能是road8／road24，班组和容量必须严格对应，付费键值必须与初始人数和当时固定配方相符。大队必须在装备竣工之后出发。
- 每个当前大队引用不同assetId，包含空车返程；引用不存在的资产、同资产双用、第三支队伍、跨来源重复partyId均拒绝。
- 新Origin回执的initial/alive/dead、原始cohort计数及年度死亡按该回执capacity验证，不能统一把所有旧回执上限放到24；旧8人回执仍只准8。
- 历史回执只核验当时的付费资产和快照，不要求现在仍有4个工人、可通行道路或足够维护仓；欠供、退休、停运是合法的可恢复存档状态。
- 迁移在克隆上校验、初始化、复验后原子替换；失败保留原档。不得因少一套装备就删掉16名旅客来让存档通过。

## 7 能改善多少，额外养得起多少

以下为满载、两队交错每120秒发一批的长期理论上限，不扣候床、来源限制、死亡、缺料和施工占用；不等于最终新增存活居民。

| 配置 | 运输工 | 理论迁入／历史年 | home年度旅费及额外维护 |
| --- | ---: | ---: | --- |
| 两小队 | 4 | 40 | 粮240、药8、工具8 |
| 一大一小 | 6 | 80 | 粮480、药16、工具17.25、木5、零件0.5 |
| 两大队 | 8 | 120 | 粮720、药24、工具26.5、木10、零件1 |

两大队相当于每10秒额外预算粮12、药0.4、工具约0.4417、木约0.1667、零件约0.0167。这些费用由home单仓承担；不能拿三城合计净正代替home能支付。设计24中三城基础粮余量仅14.6的保守实例，扣大队旅费后仅余2.6，尚未扣全部旧合同、外站及其他交通，不能据此宣布全链已经稳定。

新两来源合计2160累计额度，在满载无损理想情况下需要90趟大队，最后一批约18历史年抵达，4×约45现实分钟；最后一支空车返回还需120模拟秒。净增1600至少要67趟（66趟24人＋末趟16人），理想最后抵达约8040模拟秒，4×约33.5现实分钟。期间居民照常出生和离世，实际抵达需求仍按设计24的人口恒等式计算。

## 8 下一步开发范围与验收

建议新增`content/passenger.js`、`src/postwar/passenger.js`、`tests/passenger.test.cjs`。CivilPassenger提供纯`assets/availableAsset/profile/quote/cost/staffedParties/validate`，以及`init/refresh/reset`；来源扣人和旅队推进仍分别由Origins、Urban拥有，不复制控制器。

建议固定调用合同：`assets(s)`从home竣工记录派生装备；`availableAsset(s)`排除全部在途引用；`profile(s,party)`读取固定快照或合法旧8人默认；`quote(s,{source,target,preference})`只读返回包含`sourceQuote/transport/cost`的完整可行方案，失败返回`reason`；`staffedParties(s)`返回实际具备完整班组的partyId集合。`cost(profile,initial)`使用唯一配方，界面和验证都不另算一套费用。

Origins的`quoteParty/quoteReason`额外接收`options.capacity`（批次仅8或24，singleton永远1），纯报价可以检查24人但不能自行授予装备。`commitDeparture`追加第五参数transport，默认仅兼容旧8人；24人提交须复验真实完工资产、空闲班组及快照，并保存到原回执。Urban在全部检查后统一付费、调用该提交、加入旅队；最后两步之间不再放可失败的资源或资格检查。

必要共享接线限于：

- content/services与Services：增加home专属passengerfleet项目，沿用2营建工和完工历史；岗位wrapper增2运输席；校验设施与完工记录上限随新增2项正确扩展，地方拒绝该工程。
- Urban：最大可行批次事务、不可变快照、资产占用、实际crew预留与移动核验、按初始人数验证旅粮上限；原生街区中的规模和工程状态文字。
- Origins：1—24家庭组报价与原因、按快照capacity校验新回执、抵达／死亡／返乡快照一致性，保留所有原总账与旧8人兼容。
- adapter/index/platform：加载与一次初始化、完整校验、原生刷新。Regions继续使用同一Catalog岗位容量和Urban预留接口；不改货车载重或线路时间。Society继续拥有home劳动力和退休调岗，不加另一套工人名册。
