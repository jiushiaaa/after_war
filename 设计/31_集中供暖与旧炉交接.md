# 集中供暖与旧炉交接

2026年11月1日。接续设计28第3节，本文记录本轮**已实现规则、存档合同和验收边界**，以当前 Heating、Services、Hearth 及生产／迁居入口为准。

全套 **467/467通过**，日志 `/tmp/postwar-heating-full.log`；其中 Heating 14项、Hearth 9项。自然UI已研究集中供暖、付费建成home两站、4名实际供热工供1200人份覆盖1164人，并明确交接、检查手动缺供提示后恢复电动。原始导出63已原生重载；64为手动测试后存档。**自然应急工作间仍由主线程继续验证，不能据规则测试称已自然验收。** 详见第7节。

## 1 作用与阶段边界

集中供暖通过研究、付费工程、真实班组和燃料接替旧维修间。旧档继续原炉火，直到玩家明确交接；研究、建站或通电都不会自动交接。各地分别使用本地人员、仓库和当轮电力，home热量不跨地图供暖。

交接后缺热会显示覆盖不足，阻止不满足供养条件的新批次迁居和到站入籍，使相关城镇／城市／Metro持续资格检查不通过；已经取得的历史城市身份不被删除。人口继续按原年龄、口粮、医疗与运输规则变化，不因缺热删人或改名册。

**本片没有寒季、冻死、冷害健康扣减、热能仓或跨城热网。** 缺热不冻结全部生产和修复：住房、Services工程、运材、采矿、手动零件及能源恢复仍按原有材料、人员、健康、许可与工时规则运行。原Room建设入口另有小工作间条件，见第5节。

## 2 研究、工程与运行配方

| 项目 | 当前实现 |
| --- | --- |
| `district_heating` | 界面名“集中供暖”；前置 `municipal_engineering`、`power`，home已有历史城市后发现；钢12、零件8、知识80，基准300模拟秒，按原研究速度推进 |
| `heatingplant` | 供热站；木200、铁40、钢30、零件16、工具20；2名实际成年人同时在岗累计施工300模拟秒；每地最多4座 |
| 建站许可 | home须实际公共诊疗和教学岗位；地方还须已同意市政发展、正式镇制，以及本地田片、诊疗、学舍和医护／教师。**地方不必先成为城市** |
| `heatingworker` | 界面名“供热工”，每站最多4席；home由玩家分配，地方在原统一劳力计划中分配。不新增居民、不重复计算同一人的工作 |
| 电动，每站每10秒 | 2供热工、煤0.8、零件0.02、同一当轮电力池1电，供600人 |
| 手动，每站每10秒 | 显式选择；4供热工、煤1.2、零件0.02，不用电，供300人 |

研究不赠站。home开工原子支付全额材料；地方通过现有Services货运逐批收齐，消耗工程buffer后开工。同地点原施工互斥继续有效。home用 `servicebuilder`，地方用 `builder`；`workedSeconds`每个满足2人在岗的模拟秒加1，不能把两人工时相加后150秒完工。缺工暂停，同秒重复调用和读档不补进度。

供热站工程及竣工账保留 `paid/workedSeconds/startedAt/lastWorkedAt/completedAt`，地方另保留真实运材 `receipts`。旧工程不补造新凭据。设施仅由Services记录，Heating不另建建筑、人口或仓库。

热容量不乘政策、健康或工业产出倍率，按完整站次实付。发电机已花的煤不能抵扣锅炉煤。Services内顺序为**水务→药剂→供热**，随后把剩余当轮电力交回原工业流程；不重读总generation，不把供热用电当作晋城的机械生产用电。未交接试运行也真实收费。

每600秒一年，一站持续电动直接用煤48、零件1.2，持续占2工与1电；手动用煤72、零件1.2、4工。发电机自身消耗另计。1200人至少需2座电动站或4座手动站；4站的手动总上限仅1200，不能承诺1800／2400人的全覆盖备用。

## 3 服务凭据与明确交接

Heating唯一拥有运行凭据、模式及交接状态，主要接口已接入：

| 接口 | 实际责任 |
| --- | --- |
| `data/stations/manual/handed` | 纯读该地供暖账、Services站数、模式和交接状态 |
| `ensure(s,id)` | 仅有真实完工站时建账；正常旧档无站不创建字段 |
| `run(s,id,{run,powerAvailable})` | 使用真实劳力、原付款回调及剩余电，返回 `used/demand/capacity`；同一elapsed不重复付费 |
| `capacity(s,id)` | 只认 `economy.at ≤ elapsed ≤ economy.at+10` 的实付容量，旧证据不能永久暖城 |
| `covered(s,id,extra)` | 未交接返回true以保留旧制；交接后按现人口加明确传入的额外人数检查当前热量 |
| `forecast(s,id,extra,retire)` | 深克隆上按下一真实生产边界运行完整生产；extra支持真实cohort数组，纯人数回退按不工作的17岁居民估算，不虚构新增成人劳力 |
| `growthReason(s,id,extra,forecastCopy)` | 检查当前和下一轮容量；可复用调用方已按真实名册产生的forecast copy |
| `handoverReason/handover` | 点击时重新核验；失败不改状态，成功只记录一次交接和当时证明 |
| `workshopReady/recoveryReady/emergency` | 原Room施工、小聚落单人恢复及实付应急工作间，见第5节 |

建站后即出现试运行和交接控制，不要求地方再晋城市。按钮在条件不足时禁用，点击仍重新检查：

1. 至少1名本地居民；有效实付容量覆盖现居民及该目的地全部在途住房预留。
2. 预测使用 `CivilUrban.waiting(s,id)` 的**真实年龄名册**，按 `Services.nextSettlementAt` 推进到下一真实生产边界。不能把儿童、老人换成成人来补电工，也不能无条件elapsed加10错过生产时点。
3. home至少保留2名真实采木工，即成年劳力扣除全部已分配岗位后的余额；home预测已去掉工匠2木／10秒，不免费配人。
4. 本地仓保留近轮实际锅炉支出的三轮底储：每个电动运行站煤2.4、零件0.06；手动煤3.6、零件0.06。它是30秒锅炉直接投入，**不是120秒全服务保障，也不证明长期净收支为正**。

成功交接不另收工程费。home旧自动添柴及固定2木／10秒同时退出，真实采木产出仍保留。地方只交接当地，不扣其本来没有的2木、不改home炉火。缺热或应急都不撤销交接、不返还固定产木。

旧 `game.fire/temperature` 保留为记录，不再作为城市热量凭据。home的fire、temperature活动任务及未消费的存档timer键被清除；残留旧回调也有guard，不能再扣木或重排任务。未交接的早期生火、守火、剧情升温不变。

## 4 迁居人数与真实年龄只算一次

儿童、成人和老人每人都占1份覆盖，不按口粮权重折算。`growthReason`不会自行重复添加waiting，由调用方传入这次需要同时照顾的名册。

| 入口 | 当前口径与后果 |
| --- | --- |
| 批次报价／提交 | 现人口＋该目标已有waiting＋候选真实名册；原来源、旅费、服务与完整运输班组仍核验，失败不付出发费 |
| 即时singleton | 报价后按现人口＋waiting＋这一真实来源居民检查，不抢已出发旅队的热容量；仍付原6粮并写原来源回执 |
| 本队到站 | 现人口＋该目标全部waiting，已包含本队，不再加一次；home和地方都检查当前及下一轮 |
| 地方服务预测 | 先由 `Municipal.forecast(s,id,cohorts)` 产生真实名册的完整生产copy，再交给Heating；儿童和老人不能贡献成人岗位 |
| 到站缺热 | 原旅队进入 `held/services`，保留人、预留床和来源账，按原规则消耗旅粮并可返乡；入籍前不记admitted |
| 出生、死亡、完工住房 | 原名册与床位保留，不补热、不回收住房；下一轮生产及后续增长／持续资格检查读取新人数 |

`Urban.receive`入籍前再次核对当前热量和其他预留；本队已在 `u.parties` 时不重复计入。真实接纳后才闭合来源账。交接预测和实际到站预检都传waiting真实名册，不能拿只有人数的成人估算代替。

## 5 断供、应急与修复

调岗、采木、采食、采煤、恢复发电、原手动机械产零件、实付修路、运材和建供热站均保留，不增加“先暖全城”的通用前置；这些行为仍支付原投入。住房也可建，能否接纳新人另查。

`Room.build`本体和adapter建设按钮已统一读取 `workshopReady`：未交接仍需原温度至少2；交接后需实际热量至少20人份，或有效应急工作间。不只改按钮，也不临时抬高temperature绕过本体。

home交接后，当前既无20人份正常热量、也无有效应急服务时，可付5木开启120模拟秒工作间。记录为 `at/until/capacity:20/cost:{wood:5}`，`elapsed===until`即失效。有效期内重复点击不再扣款、不延时。原生点火和添火函数均不能重启旧自动守火。

应急工作间支持修理，也允许原即时singleton从真实来源逐人恢复小聚落，条件是 `home人口＋全部在途预留＋1≤20`。仍需床位、许可、6粮和实际来源，绝不赠成人。`receive`仅承认 `transport===null`、没有 `party.state`、人数1的即时例外。第21人、新批次、已发批次及其他目的地不能借同一份应急热获得全城覆盖或入籍许可。

手动每站4人是真实劳力；home两站但只有4名供热工时，手动只运行一站，得到300人份。补资源或切回电动须等下一生产轮，不能同轮重跑锅炉。地方成年人口全灭后的完整重建不属于本片已验证范围。

## 6 存档、界面与文明史

可选状态为 `c.heating={schema:1,nodes:{...}}`。有站节点保存 `introducedAt/manual/handedOverAt/handover/economy/emergency`；introducedAt对齐首座站竣工。economy记录 `at/mode/stations/workers/requested/paidStations/capacity/used/demand/cost`；handover保存当时人口、预留和实付证明快照，不用今天的人口反写历史。

合法旧档无站时不新增热网、燃料、交接或历史。有新站却删除Heating账、显式null、伪造容量／煤件付款／施工秒数、未来时间及错配工程均拒绝。生产在同秒施工完工之前发生时，允许旧凭据站数位于“该秒前已竣工数”和“截至该秒竣工数”之间；下一生产轮才用新站，合法即时存档不会因新站刚完工被拒。

控制附在现有街区／市政公用设施区域，没有新管理标签。实际UI：

- 研究“集中供暖”、工程“供热站”，提示材料、2人300秒及运行配方。
- 完工后显示“供暖试运行”或“日常供暖”：`容量 / 现居民 人份`、电动循环／手动轮值、近轮实付煤／零件和用电；不足时写“覆盖不足，新的批次接纳暂停。” **摘要没有单列在途预留，也没有逐项缺料诊断表**，预留与下一轮条件由实际检查及交接提示承担。
- 控制为“安排手动供暖／恢复电动供暖”“交接日常供暖”。home交接提示明确旧炉自动添柴及2木收入退出，成功后隐藏交接按钮。
- home旧地点改为“公共维修间”，折叠区“旧炉与应急工作间”；健康时“供热站已接管”，缺供时提示不足或应急剩余秒数。原添火隐藏，点火入口改“开启应急工作间”，保留原按钮计时子节点。
- 故障更新摘要，不反复弹出强制事件。供热站沿Services工程史记录；“供暖交接”类别记录当时容量、居民和预留。历史是持久账的只读投影，不补造未知旧时间。
